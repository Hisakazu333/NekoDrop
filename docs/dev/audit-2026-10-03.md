## P0 — 用户可直接感知的 bug

| # | 位置 | 问题 |
|---|------|------|
| P0-1 | `src-tauri/src/commands/mod.rs`（58 个命令全部为同步 `pub fn`，0 个 async） | 按 Tauri 2 规则，未标 `async` 的命令在**主线程**执行。`send_paths_to_code/device`（mod.rs:742/752）在命令内同步完成连接+逐文件传输+重试，**传输期间整个应用冻结**；`request_device_pairing`（mod.rs:269）同步等待对方用户决定（最长 300s）。这大概率就是"传输时界面卡死/点不动"的根因。 |
| P0-2 | `crates/nekodrop-network/src/transport.rs:98` | 全链路只有 connect 4s 超时，连接后**无 read/write 超时**。对端假死时接收线程永久挂死，且取消标志只在两次读之间检查——**卡在 read 里时取消也失效**。 |
| P0-3 | `InboxDrawer.tsx:39-45` / `InboxDropdown.tsx:39-46` | 「拒绝/允许」两个按钮行为完全相同：`handleAction(action, accept)` 的 `accept` 参数从未使用，都只是删除请求。用户点「允许」实际什么都没授权。 |
| P0-4 | `AppContext.tsx:566` + `App.tsx:21-34` | 有待处理 offer/配对请求时每 1.2s 强制 `setMode("receive")`，而 App.tsx 路由**没有 "receive" 分支**——用户正打字时被反复拽走，且实际渲染的是 default 分支（发送工作台）。 |
| P0-5 | `resume.rs:179-181` + `received_file.rs:141-146` | 传输中断留下的 **0 字节 `.nekodrop-part`** 会让同路径文件**永久无法再接收**（resume 判无可续传 + receive 判 partial 已存在直接报错），需手工删文件。 |
| P0-6 | `received_file.rs:213-218` | 校验和不匹配时**保留已损坏的 partial**，下次续传基于坏数据必然再失败 → 死循环失败。且取消路径反而删 partial（与续传语义相反）。 |

## P1 — 高风险缺陷（条件触发）

- **`start_receive_once` check-then-act 竞态**（mod.rs:1205-1212 检查后放锁，1280 直接写入不复核）：并发调用会泄漏监听线程和端口，两个线程互相覆盖状态。正确写法在同文件 mod.rs:878-887。
- **TitleBar 监听器每渲染重挂**（TitleBar.tsx:25,45-52）：`getCurrentWindow()` 每次 render 返回新实例作为 effect 依赖；1.2s 轮询导致反复注销/注册 + 未处理 rejection。
- **设备离线后仍可被选为发送目标**（AppContext.tsx:452-457,365-371 + TransferZone.tsx:77-81 重复推导）：`selectedDeviceSnapshot` 永不过期，离线/失信设备继续显示为合法目标，发送必失败。
- **`list_transfers` 双通道乱序覆盖**（AppContext.tsx:605-608）：无 in-flight 守卫/请求序号，删除传输后旧响应可把已删记录显示回来；`scanPaths`（823-840）并发时慢响应覆盖新扫描结果。
- **网络全链路无 IO 超时**（nekodrop-service/lib.rs，`set_read/write_timeout` 出现 0 次）：发送方对不可达主机挂到 TCP 栈超时（分钟级）。
- **本地桥接授权码可自行推导**（mod.rs:4575-4599）：sha256 输入全部来自请求方，恶意本地应用可算出"正确"码，应改 CSPRNG。
- **bundle JSON 直接覆盖写，无 temp+rename/fsync**（bundle.rs:970-977）：崩溃留截断 JSON；导入回执损坏则回滚永久不可用。SkipConflicts 导入策略（bundle.rs:580-587）也是直接写目标目录，无原子性。
- **传输历史写盘失败被 `let _ =` 吞掉**（mod.rs:1010,1048,1548,4808）：磁盘满时 UI 与历史静默不一致。

## P2 — 结构性屎山（维护成本根源）

1. **`commands/mod.rs` 共 11,561 行** = 5,385 行生产码 + 6,170 行测试（115 个）。单文件承载 58 个命令、8 个子系统。其中 local bridge 子系统约 2,900 行几乎自包含，是最佳拆分起点；已有 `_at` 后缀参数化风格和 15 个兄弟模块，拆分基础好。
2. **`AppContext.tsx` 1,465 行**：8 个状态域（设置/发送队列/发现配对/传输/接收/收件箱/本地桥接/UI chrome）塞一个 Provider，~40 个 useState，context value 未 useMemo，1.2s 轮询驱动全树重渲染。
3. **三段式复制粘贴已漂移**：send/import/rollback 的分发、retry 响应、matcher 各三份近乎相同代码（mod.rs:2045-2202 / 2300-2509 / 3971-4135）；错误处理已出现不一致（import 失败停在 running 无终态，mod.rs:2754 vs send 会记 failed，2886-2914）。
4. **前端死代码量大**：`deviceDisplay.ts`、`settingsView.ts`、`transferHistoryDetails.ts`、`pairingFailureAdvice.ts`、`receiveDiagnostics.ts`、`securityState.ts` 六个模块无任何调用方（但各自有测试——测试也在测死代码）。
5. **单一全局 busy 标志**被 ~30 个操作共用（AppContext.tsx:340），并发时先结束者提前解锁 + 多处语义错标。
6. clippy ~50 条警告：17 redundant closure、18 too-many-arguments、若干 dead code（`handle_local_bridge_request_with_auth_at`、`import_staged_bundle_at`、`set_device_name` 为纯死代码或测试专用）。

## P3 — 值得记下的中低优先级问题

- 锁中毒被 `if let Ok(...)` 静默吞（mod.rs 约 20 处），中毒后发送功能永久"已有任务进行中"且无日志；`device_identity.rs:31/45` 的锁 expect 是仅有的生产 panic 源。
- `now_ms()` 在 5 个文件重复定义；mod.rs 的定义放在 6,100 行测试之后（clippy: items after test module）。
- 事件 ID `{transfer}:{phase}:{updated_at_ms}` 同毫秒碰撞，长轮询唤醒条件可能失效（mod.rs:3795-3798, 4613-4617）。
- `is_retryable_send_error` 用子串匹配错误文案（含中文）判断可重试性（mod.rs:1082-1123），"host not found" 被误判为不可重试。
- 一个损坏的暂存 bundle 目录让 `list_staged_bundles` 整体失败（bundle.rs:436-442 连坐），其他 bundle 全部不可见、清理也失效。
- `transfer-{millis}` 作传输 ID，同毫秒可碰撞（service lib.rs:1648-1654）。
- 接收循环 120ms 忙轮询（mod.rs:1623-1625）；`stop_receive_once` 与接收线程双写终态顺序不定（L6）。
- 前端 `keepIfEqual` 每 5s 对大数组做双份 `JSON.stringify`（AppContext.tsx:119-133）；三处「待处理数」过滤器口径不一致（InboxDrawer 含 imported、InboxDropdown/TitleBar 不含）；ActivityInspector 重复实现进度公式且与 canonical 偏离。
- `sendFiles` 用未 trim 的 connectionCode（AppContext.tsx:901），粘贴带空格的码可通过校验但发送失败。
- 自动开收件失败后永不重试（AppContext.tsx:398-406，ref 前置置位不复位）。
- appearance 同步 effect 写了两份（AppContext.tsx:332-337 与 379-382）。
- sidecar：绑定 0.0.0.0 时连接码 host 不可用（main.rs:73-77）；裸 IPv6 解析错误（127-133）；只有明文模式。
- 明文 LegacyPlain 模式零完整性零认证（设计如此，兼容用），但配对码明文传输且 crate 层无限速原语（tcp_file.rs:873-886）。
- 前端测试 143 个里大量是对源码做正则匹配的"文本断言"（如 realtimeSnapshot.test），不是行为测试；P0/P1 所在区域几乎零行为覆盖。

## 建议的整改路线

**阶段一：止血（修 P0，约 1-2 天工作量）**
1. 命令 async 化：传输/配对/长等待命令改 `async fn` 或 `#[tauri::command(async)]` + `spawn_blocking`，UI 不再冻结。
2. `transport.rs` connect 成功后 `set_read_timeout/set_write_timeout`（如 30s），收发循环保留取消检查。
3. partial 文件生命周期三处修正：mismatch 删 partial、0 字节 partial 视为不存在并清掉、取消保留 partial 供续传。
4. 收件箱 accept 语义：命令带 `accept` 布尔，前端传下去（或短期两按钮合一去误导）。
5. 删掉 AppContext.tsx:566 的强制 setMode，改角标提醒；App.tsx 路由补 receive 分支。
6. TitleBar `getCurrentWindow()` 用 `useMemo` 固定 + async 补 catch。

**阶段二：高风险竞态与一致性（P1，约 2-3 天）**
- start_receive_once 改为锁内 check-and-set；selectedDevice 过期清理并单一出处；refreshTransfers/scanPaths 加请求序号；授权码改 CSPRNG；`write_json_file` 改 temp+fsync+rename。

**阶段三：拆屎山（P2，可在功能间隙分批做）**
- `commands/mod.rs` → `commands/local_bridge/`（dispatch/queue/authorizations/matching/events）+ `receive.rs` + `send.rs` + `devices.rs` + `settings.rs`，测试随代码走。
- `AppContext.tsx` → 先拆 LocalBridgeProvider 和 SettingsProvider（最自包含），context value 加 useMemo。
- 合并三胞胎代码为泛型/参数化；删 6 个死代码前端模块及其"文本断言"测试；清 clippy。

**阶段四：测试升级**
- 用 renderHook + mock invokeCommand 给轮询乱序、监听清理、accept 语义等写行为测试，替代正则文本断言。
